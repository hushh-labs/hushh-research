Executive summary

Hushh is giving every person their own always-on private agent — a per-user “Private Cloud Compute” instance we call 🤫 Agent One. A person’s phone number is the master key; every access to their data carries a consent receipt; and Hushh is the consent, identity, and audit authority. The agent runtime is portable across compute backends behind one interchangeable interface.

The deployment decision

Anypoint is the primary deployment target — you have a dedicated team to operate it, and CloudHub 2.0 / Runtime Fabric give us a governed, compliant home for the per-user runtime. We ran the initial live validation on GCP (our fastest path to proof); because the runtime sits behind a backend-neutral seam, making Anypoint primary is a configuration and priority choice, not an architecture change. The Anypoint adapter already renders the equivalent AMC descriptor today.

This revision keeps the technical substance of the prior draft and adds two things: it makes the Anypoint realization concrete (§5), with example snippets for provisioning, auth, governance, and data mapping (§5, §7), and it links the published branch documentation (Appendix B) so your team can read the implementation directly.

3

The direction Hushh is taking

One logical agent per person, portable across compute backends. The design rests on five ideas:

Phone number = master key

Each person receives one sovereign, opaque identity — a HusshID derived from their verified phone number — which is the address by which they, and with consent others, reach their agent.

Consent-first (PCHP)

Every data access carries a receipt on a visible ledger. Consent is not only enforced at Hushh’s door; the agent carries it outward to exercise the person’s data rights.

Zero-knowledge pod

Each agent holds its own encryption key. Hushh stores only public keys and wraps scoped data to them, so plaintext exists only inside the person’s isolated pod and on their device.

Slim pod: agent + storage

The pod runs the agent and its storage only. Consent issuance, audit, and administration stay central at Hushh — smaller, safer, and portable.

One logical architecture, many compute backends

Behind one interface, the same agent runs on the Anypoint enterprise runtime (the primary target), on Hushh-hosted or user-owned GCP, or on edge hardware the person owns. Adding or swapping a backend never changes the agent, the identity, or the consent model.

The role of Anypoint

As the primary target, Anypoint hosts the per-user runtime and carries the integration and governance lanes. One of these — the OmniGateway on CloudHub 2.0 — already runs in our platform today.

Per-user runtime hostThe primary home for the slim pod — a Mule app on CloudHub 2.0 / Runtime Fabric, isolated in a Private Space.
Enterprise integrationThe connective tissue to Salesforce, CRM, and enterprise data — extending the existing OmniGateway pattern.
Gateway governanceGovern A2A and MCP traffic via the Flex / AI Gateway: PII detection, rate-limiting, and trusted-agent identity.
MCP server (Mule app)Expose enterprise tools and connectors to agents over the open MCP protocol.
Data-rights toolsetConnectors behind the agent’s outbound work — discover, access, correct, share, and request removal of PII — each with a receipt.

Where Hushh stays authoritative

Anypoint hosts and governs, but never becomes the consent authority: it reaches personal data only through Hushh’s consent tokens, and never holds or issues consent itself. Identity, consent issuance, and the audit ledger remain central at Hushh.

The Hushh ⇄ Anypoint contract

A small contract that mirrors the client-credential + gateway pattern we already run. Four parts, with example shapes.

a · Provisioning / teardown / status

Idempotent by hushh_id; realized on the AMC Application Manager API (Snippet 1).

POST {base}/agents/provision
{ "hushh_id": "ha1abc234def", "phone_e164_hash": "…", "region": "us-e",
  "consent_binding_ref": "cbr_…" }
# -> { "anypoint_agent_id": "one-pod-ha1abc234def",
      "a2a_route": "https://a2a.hushh.ai/u/ha1abc234def", "status": "provisioned" }

DELETE {base}/agents/{hushh_id}     # idempotent — already-gone = success
GET    {base}/agents/{hushh_id}     # status/health, for the reconcile loop

Payloads carry only opaque or derived identifiers — never a raw phone number, never a private key, never user data.

b · Governance policy (Flex / AI Gateway)

Snippet 3 · Flex Gateway — govern agent traffic to the pod
- policyRef: { name: rate-limiting }
  config: { rateLimits: [{ maximumRequests: 60, timePeriodInMilliseconds: 60000 }] }
- policyRef: { name: pii-detection }        # DLP: mask/deny on detected PII
- policyRef: { name: jwt-validation }       # trusted-agent identity (HCT-bound)

c · Data-rights transform (DataWeave)

Snippet 4 · a correction request mapped to a Salesforce update
%dw 2.0
output application/json
---
{
  recordId: payload.subjectId,
  fields: payload.corrections,          # the fields to rectify (GDPR Art. 16)
  requestedBy: vars.hushhId,
  consentReceipt: vars.receiptId        # PCHP receipt travels with the action
}

d · Mail-event trigger (the always-on inbox)

The agent reviews mail and drafts replies, so it must wake the instant mail arrives — without Anypoint (or Hushh) ever reading the message. The trigger is a Mule flow whose source is a provider-native push: Gmail users.watch() → Google Pub/Sub (an inbound HTTP listener for a Microsoft Graph webhook is the Outlook parity). It is a doorbell, not a mail-opener: it forwards only the event metadata — { emailAddress, historyId }, never the body — to wake the user’s pod, and the pod then fetches the changed messages with the user’s own mailbox token and decrypts them in-process.

Snippet 5 · Mule flow — the mail-event listener (metadata only)
<!-- Mule app: the mail doorbell. Source = provider push; it never reads the body. -->
<flow name="one-mail-wake">
  <!-- SOURCE: Gmail watch -> Pub/Sub (Outlook parity: an HTTP listener for a Graph webhook) -->
  <gpubsub:message-listener subscription="one-mail-${hushhId}-sub"/>
  <ee:transform>                       # keep ONLY the event metadata
    { emailAddress: payload.emailAddress, historyId: payload.historyId }
  </ee:transform>
  <http:request method="POST" path="/wake" config-ref="pod-${hushhId}"/>
  # the pod fetches the changed mail with the user's OWN token — Anypoint never sees the body
</flow>

Why not just call an email MCP tool?

MCP tools are the agent’s hands — read a thread, draft, send — used after it wakes. They are not its ears: there is no watch/subscribe primitive, so using MCP as the trigger means polling, which is neither immediate nor scalable. The provider push is the ear; MCP is the hand. Watches expire (Gmail ~7 days, Graph ~3), so a small renewal job re-arms them; delivery is at-least-once, so the pod dedupes on historyId. In the user-owned-cloud (BYOC) tier the whole trigger — topic, subscription, and pod — lives in the person’s own project, so neither Anypoint nor Hushh sees even the “new mail” event.

Implementation & compliance

Phasing

  • Done (Hushh side): the backend-neutral seam, the slim pod, the consent model, and passkey / hardware-key sign-in are built; the deploy loop is validated on GCP. The Anypoint adapter renders the AMC descriptor today.
  • Next (joint, Anypoint-primary): confirm the §9 items; stand up a Connected App; deploy the pod as a Mule app on CloudHub 2.0 in a Private Space via AMC; apply the Flex/AI Gateway policies and the MCP Mule app; wire the connectors for data-rights.

Compliance posture — stated honestly in pursuit

  • Commercial Anypoint carries SOC 2 / ISO 27001 / PCI / HIPAA / GDPR — the baseline.
  • FedRAMP is Moderate and only in MuleSoft Government Cloud; commercial CloudHub is not FedRAMP. If FedRAMP High is the target, it is a distinct environment — we need to confirm the target with your team.
  • Certifications are presented as “in pursuit” until an independent assessor confirms them.
