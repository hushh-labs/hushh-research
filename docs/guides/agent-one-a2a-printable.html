External Developer Brief

Hussh Agent One A2A Integration

A printable handoff for external developers and partner agent platforms such as Salesforce Agentforce. Fill in the credential fields separately and keep real tokens out of the document.

What This Enables

Agent One is the Hussh private-agent coordination surface. A partner agent sends a user request to Agent One, and Agent One either answers directly or routes the request internally.

In this brief, A2A means agent-to-agent integration over normal HTTPS API calls. The partner does not need a special transport: it discovers the Agent Card, then calls the Agent One message API with the required developer and consent headers.

Important: Share the document without real developer tokens or consent tokens. Send credentials through a secure channel after the partner has been approved.

Credential Sheet

Field Value
Hussh base URL https://api.uat.hushh.ai
A2A agent id agent_one
Required consent scope agent.one.orchestrate
Developer app agent id developer:app_________________________________
Developer token Provide separately through a secure channel.
User consent token Generated after the user approves agent.one.orchestrate.

The developer token is setup-time partner authentication. The consent token is part of the runtime flow: request approval first, then use the user-approved token to execute Agent One. 

HUSHH_DEVELOPER_TOKEN="<developer-token-issued-by-hussh>"

How To Get Developer Credentials

  1. Open https://uat.kai.hushh.ai/developers and sign in with Google or Apple.
  2. Enable developer access for the account.
  3. Copy the developer app agent id shown in the portal. It uses the format developer:app_....
  4. Copy the developer token when it is first issued. The full raw token is shown only at issue time.
  5. If the token was lost, use the portal's rotate-key action to revoke the old token and reveal a replacement.
  6. Store the token in a secure credential manager or Salesforce Named Credential. Do not paste it into prompts, docs, tickets, CRM notes, source code, or screenshots.
Credential rule: the developer token and developer app agent id are linked. Agent One rejects a user consent token if it belongs to a different developer app agent id.

Endpoints

Method Path Purpose
GET /.well-known/agent-card.json Discover Agent One metadata.
GET /api/one/a2a/card Compatibility alias for the same Agent Card.
POST /api/one/a2a/message Request consent or execute Agent One after approval.

Headers

Header When to use it
Authorization: Bearer <developer-token> Required for partner calls to the message endpoint.
X-Consent-Token: <consent-token> Required only after the user has approved Agent One orchestration.
Content-Type: application/json Required for POST requests.

Typical Flow

  1. Partner discovers Agent One through the Agent Card endpoint.
  2. Partner calls the message endpoint without X-Consent-Token to create or check a consent request.
  3. The user approves agent.one.orchestrate in Hussh.
  4. Partner calls the message endpoint again with both the developer token and the user consent token.
  5. Agent One returns an answer or routes the request internally.

Conversation Id

conversationId is created by the calling partner system, not by the Agent One A2A endpoint. Treat it as a correlation id for the partner's own session, case, chat, or workflow.

Partner system Good conversation id examples
Salesforce Case sf-case-500xx0000012345
Salesforce Agentforce session sf-agentforce-session-a1b2c3
Partner chat session partner-chat-20260706-001

Send the same conversationId on follow-up calls for the same partner-side conversation. If the partner omits it, the A2A response may return null; Agent One does not mint one for this endpoint.

Call 1: Discover Agent One

The Agent Card is discovery metadata. It tells the partner where Agent One is, what scope is required, and how to authenticate. The actual user task, such as a KYC account-opening request, belongs in POST /api/one/a2a/message.

Other agents use the card's public name, description, required scope, endpoint, and capability hints to decide whether to delegate to Hussh Agent One. Delegate when the user request needs Hussh-managed consent, user-owned personal data, KYC/account-opening data, advisor onboarding context, or privacy and vault coordination. Do not delegate ordinary CRM updates that do not need Hussh user consent or Hussh-held data. 

curl -sS "https://api.uat.hushh.ai/.well-known/agent-card.json"

KYC Data Request Pattern

For Salesforce and advisor workflows, send the business question or data need directly. A good request names the account-opening context, the KYC fields needed, and the decision the advisor is trying to make.

Use this request Do not use this
I need your legal name, date of birth, address, tax residency, and government ID details required for account opening. Send all KYC documents to Salesforce.
Before I submit this onboarding case, confirm whether your identity verification is complete and list any required account-opening items you still need to provide. Export the user's full identity vault.

A2A coordinates the KYC workflow through Agent One. Government ID details usually means structured fields needed for the workflow, not a raw ID image. If the partner needs an encrypted scoped data export, use the MCP/developer API consent lane with an identity scope such as attr.identity.*; keep raw documents out of Salesforce unless a separate explicit workflow and retention policy allows it.

Call 2: Request User Consent

Use this when the partner does not yet have a user-approved consent token.

curl -sS -X POST "https://api.uat.hushh.ai/api/one/a2a/message" \
  -H "Authorization: Bearer $HUSHH_DEVELOPER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "message": "I need your legal name, date of birth, address, tax residency, and government ID details required for account opening.",
    "email": "user@example.com",
    "conversationId": "sf-case-500xx0000012345",
    "reason": "Salesforce Agentforce is helping an advisor prepare for account opening and needs Agent One to review KYC readiness with user approval.",
    "approvalTimeoutMinutes": 60,
    "expiryHours": 24
  }'

Call 3: Execute Agent One

Run this only after the user approves the request from Call 2 and the integration has the resulting consent token.

curl -sS -X POST "https://api.uat.hushh.ai/api/one/a2a/message" \
  -H "Authorization: Bearer $HUSHH_DEVELOPER_TOKEN" \
  -H "X-Consent-Token: <user-approved-consent-token-from-call-2>" \
  -H "Content-Type: application/json" \
  -d '{
    "message": "I need your legal name, date of birth, address, tax residency, and government ID details required for account opening.",
    "userId": "user-one",
    "conversationId": "sf-case-500xx0000012345",
    "persona": "ria"
  }'

Salesforce Agentforce Notes

  1. Create a Salesforce Named Credential or equivalent secure HTTP credential for https://api.uat.hushh.ai.
  2. Store the developer token in the secure credential store, not in Apex source, prompt text, custom object fields, or case comments.
  3. Pass Authorization: Bearer <developer-token> on every call.
  4. Pass X-Consent-Token only after user approval.
  5. Store only workflow metadata in Salesforce: request id, consent status, scope, expiry, user-visible reason, audit references, and narrow approved workflow outputs.

Apex-style callout

HttpRequest req = new HttpRequest();
req.setEndpoint('callout:Hussh_One_A2A/api/one/a2a/message');
req.setMethod('POST');
req.setHeader('Content-Type', 'application/json');
req.setHeader('Authorization', 'Bearer ' + developerToken);
req.setHeader('X-Consent-Token', consentToken);
req.setBody(JSON.serialize(new Map<String, Object>{
    'message' => 'I need your legal name, date of birth, address, tax residency, and government ID details required for account opening.',
    'userId' => 'user-one',
    'conversationId' => 'sf-case-500xx0000012345',
    'persona' => 'ria'
}));

Http http = new Http();
HttpResponse res = http.send(req);

Error Handling

Status Common cause Partner action
401 Missing developer token. Add the developer bearer token.
403 Invalid consent token, wrong scope, app mismatch, or user mismatch. Re-request consent or verify token ownership.
404 User lookup by email or phone did not find a Hussh account. Ask the user to sign in or provide the correct identifier.
410 Developer API disabled in the target environment. Confirm target environment and partner enablement.
500 Agent One orchestration failed. Retry only if idempotent; include conversation id in support handoff.

Security Boundary

  • agent_one coordinates requests. It does not grant broad data access by itself.
  • Developer tokens identify the external app. Consent tokens identify user-approved authority for a scope.
  • Do not put developer tokens or consent tokens into Salesforce prompts, CRM text fields, support transcripts, analytics events, or public logs.
  • Do not send raw vault contents, private keys, KYC documents, full email bodies, or broad personal-memory exports through this A2A route unless a separate explicit workflow allows it.

Handoff Checklist

  • Have the partner enable developer access at https://uat.kai.hushh.ai/developers.
  • Confirm the portal shows a developer app agent id in the format developer:app_....
  • Copy or rotate the developer token and deliver it securely.
  • Confirm Hussh base URL for the target environment. For UAT, use https://api.uat.hushh.ai.
  • Confirm user lookup strategy: user id, email, or phone number.
  • Test Agent Card discovery.
  • Test consent-request mode without X-Consent-Token.
  • Test execute mode with X-Consent-Token.
