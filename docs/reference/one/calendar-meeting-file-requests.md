# Calendar meeting file requests: typed Drive integration

Status: implementation contract for the Calendar Insights follow-up to PR #8584. This contract does not change ordinary Drive requests or grant Calendar read access permission to share a file.

## Authority and identity

An explicit request begins with the authenticated One owner, a selected Calendar account ID, a local day and time zone, a Calendar ID and event ID, the server's occurrence and grant bindings, and a nonempty subset of `recording` and `notes`. The server re-reads that exact occurrence from the selected account. It verifies a current Google subject and email against that account's OAuth grant, verifies the requester is an attendee and not the organizer, and resolves the event's organizer email to a current, verified One identity. An active One relationship is required by the existing Drive request store. The browser supplies no organizer ID, recipient email, or file ID as authority. Unreachable or ineligible organizers receive no request; the UI offers a local copy request and existing invitation path where available.

The selected Calendar identity is a separate recipient kind in the existing sealed Drive request envelope. It contains the selected account ID, Google subject, verified email, and connection generation. The server revalidates all of these at request creation, before provider permission creation, and before requester delivery. It never substitutes the person's One sign-in Google identity. A disconnected, changed or revoked account suppresses the action and any usable link.

## Durable request and review

Calendar origin, exact occurrence, requested types and recipient identity belong in the existing encrypted `drive_share_requests.request_envelope` and its request digest. Its `(recipient_user_id, client_request_id)` uniqueness provides idempotency; the client derives a stable UUID for the same occurrence/account/type selection. Calendar requests use the existing relationship, participant, management-context, revision, review, action-directive, per-file permission, uncertain-write reconciliation, Feed outbox, and retention paths. The Calendar origin is explicit and immutable. It suppresses payment, pricing, packages, background preparation, semantic search, trusted auto-approval, One-copy and content processing for this request only. Generic Drive terms and behavior remain unchanged.

The organizer's Feed action opens the exact request. Feed's Firebase-only projection carries the typed action and generic label; exact title, time, and recipient appear only in the Vault and placement-gated review. The review shows the meeting occurrence, requester and selected Google recipient, requested types, and one Drive account. Candidate files come from exact file IDs on the verified Calendar occurrence when available, or an explicit bounded owner-initiated Drive name search. The organizer chooses each file, attests its type and occurrence, sees the exact files and viewer recipient, then confirms once. A failed manual preparation can be retried only after invalidating the prior review revision and directive. Before queueing and before the provider POST, Drive rechecks account generation, current metadata, `canShare`, supported MIME, scope, version/name, recipient identity, relationship, placement and the action directive. No title-only matching, content reads, public/domain permission, folder permission, trusted rule or automatic approval is permitted. A successful approval means queued work; it is not a sharing or access success.

## Requester verification and status

The approved exact file association remains in the existing protected request/source/permission state. A participant-scoped read supplies only successful or preexisting, unexpired approved file IDs to the Calendar artifact reader. The reader rechecks each file through the original selected Calendar account on detail, Open, Download and refresh. Existing Meet-linked files retain their Meet-scoped verification; ordinary approved Drive files require a separately consented `drive.metadata.readonly` scope on that selected Calendar account. This scope permits `files.get` metadata checks without reading file content ([Google Drive files.get](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/get), [Drive scope guide](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)). An existing Meet-only grant remains valid for Meet files; an ordinary approved file displays `permission_required` and offers the existing selected-account meeting-file upgrade once. A provider receipt alone displays `checking access`. At least one successful selected-account read makes the meeting Available; a failed recording does not hide an accessible note. A 403, 404, empty Meet listing, or an app grant too narrow for an ordinary Drive file cannot establish that no recording exists. Revocation, erasure and expired access remove links. Existing Feed events plus visible-page bounded refresh update the cards; no new notification system is introduced.

## Rollout and rollback

The intended rollout is additive code and tests on an isolated Main-based branch, a security review, one focused PR, local checks and final-SHA hosted CI. No shared-environment migration, merge, deploy or live provider share is authorized by this task. Reuse of existing encrypted request, live-source and permission tables avoids a schema change. The additional `drive.metadata.readonly` scope is classified by Google as restricted, so its OAuth verification and consent-screen readiness are a separate release gate before deployment. If a durable index or association table proves necessary later, author its forward and rollback SQL separately and require explicit shared-environment rollout authority; never infer that a migration has been applied from a passing unit test. Rollback removes the Calendar route/UI entry and stops admitting new Calendar-origin requests; existing approved permission effects continue through the established Drive management and retention contract so they are not orphaned or revoked without owner action.

Synthetic tests prove identity substitution is refused, exact occurrence and relationship checks, duplicate requests, file capabilities and stale approvals. Live acceptance needs separately approved controlled accounts and an actual organizer-owned note and recording. CI and synthetic provider stubs cannot be represented as live sharing or requester access proof.
